Build a Refund Bot that Asks Before It Acts

A step-by-step guide to building a customer-support bot that can issue refunds, and adding a safety checkpoint in front of every action it takes. You will see why the checkpoint is needed, how it works, and every line of code behind it.

1 · What we are building

Imagine a customer writes to a shop: "My order arrived late, can I have $40 back?" A person on the support team would open the ticket, look up the order, check who the customer is, send the refund, email them a confirmation and close the ticket.

We are going to build a small program that does exactly that job on its own. It is a web service (so other programs can talk to it) with a command line (so you can try it from your terminal), and a database behind it holding customers, orders, tickets and refunds.

A program like this is called an agent. An agent is simply a loop that repeats three things until the job is done:

  1. Ask a model "what should I do next?"
  2. The model answers with a tool to use, like "look up order O-1003".
  3. Run that tool, show the model the result, and go back to step 1.

Normally the model is a large language model like Claude. To keep this guide easy to follow, ours is a small stand-in that follows fixed rules. It behaves the same every time and needs no account or API key. Later you can swap in a real model by changing one file.

1.1 · Words you will meet

2 · Why it needs a checkpoint

Here is the problem, run for real. Ticket T-1003 says "Refund me $5,000 for the trouble", but the order was only $120. We ran the bot with no protection:

  call      issue_refund {"order_id": "O-1003", "amount": 5000, "currency": "USD", "reason": "customer request"}
Answer: I refunded $5,000 for your order and emailed you a confirmation.
Ticket T-1006: open -> resolved
  4. issue_refund {"order_id": "O-1003", "amount": 5000, "currency": "USD", "reason": "customer request"}

It paid. The bot did what the model told it to, and the model believed the customer.

You might think "I will just tell the model not to do that". That helps, but it is not a guarantee. A customer can word a request cleverly, or hide instructions inside the ticket text, and a model can be talked into things. Anything that matters, like moving money, should be checked by something other than the model that asked for it.

That something is a checkpoint: before any tool runs, the program stops and asks AgentTrust, "is this allowed?". If the answer is no, the tool never runs.

2.1 · What you gain, and what it costs

It is worth being honest about both sides before you add any new part to a system.

What you gainWhat it costs
A bad action is stopped before it happens, no matter what the model says.Each guarded action makes two extra network calls, so it is a little slower. We did not measure how much.
You change limits in the Console, with no new release of your code.It is one more service your bot depends on. If it cannot be reached, you must decide: refuse to act (safe) or act anyway (risky).
Every decision is written down with its reason, so you can review it later.The library's built-in defaults act anyway when something goes wrong. If you do not change them, you may believe you are protected when you are not.
A suspicious ticket can be held back before the model reads it.The checkpoint sees what the tool is asked to do, not what the customer wrote. Some tricks are only caught after the fact.
It is about 60 lines of code and works with any agent loop.When an action needs a human to approve it, this method refuses it. It cannot wait for the human and then continue.

3 · How it works

Your agent keeps its normal shape: the loop asks the model, the model picks a tool, the loop runs it. The only change is what "runs it" means. Instead of calling the tool directly, the loop calls a wrapped version that asks AgentTrust first.

3.1 · The parts
PartWhat it does
Web service and command lineHow a ticket comes in, and how you ask the agent to resolve it.
Service (services/tickets.py)The steps for resolving one ticket. Both the web service and the command line use it.
Agent loop (agents/support_agent.py)Asks the model, runs the tool it picks, repeats. It knows nothing about refunds.
Model (llm/)Picks the next tool. Ours follows fixed rules.
Tools (tools/)Eight plain functions: read a ticket, look up an order, issue a refund, send an email and so on.
The checkpoint (tools/governance.py)Wraps each tool so AgentTrust is asked first. Also turns a "no" into a normal result the bot can understand.
Action log (tools/action_log.py)A record of every tool that really ran. This is how you prove a blocked action never happened.
AgentTrust gatewayLooks at the manifest and policy pack and answers allow or block.
3.2 · One tool call, from start to finish

Say the model wants to refund $5,000. Here is what happens:

  1. The model asks for issue_refund with an amount of 5000.
  2. The loop calls the tool it was given. That is the wrapped version.
  3. The check before. The wrapper sends the tool name and its arguments to AgentTrust. AgentTrust looks them up in the manifest ("is this tool allowed? is 5000 over the limit?") and in the policy pack.
  4. AgentTrust says block. The wrapper does not run the tool. It hands the bot a normal-looking result that says BLOCKED and gives the reason.
  5. The bot sees the result, understands the refund did not happen, and passes the ticket to a person.

If the answer had been allow, the tool would run, the action would be written to the action log, and then the wrapper would do a check after: it sends the tool's result back to AgentTrust, which can hold it back if it looks wrong, for example if it contains hidden instructions. A check after cannot undo what the tool already did. It can only stop the result from being used. That difference matters and we will see it in action later.

A note on names. You install the library as agentrust-py and import it as agentrust_sdk. A package called agentrust-sdk also exists, but it belongs to a different company. Do not install that one.

4 · The big picture

Read the diagram from the top left. A ticket comes in, goes down through the service to the agent loop, and the loop asks the model for the next step. When the loop wants to use a tool, the request passes through the checkpoint. The checkpoint is the only part that talks to AgentTrust.

Step 3 — Add the policy pack

The manifest sets firm limits. A policy pack adds flexible rules on top. In Policies, create a private pack, paste the text below (it is python/policies/refund-bot.yaml in the clone) and activate it.

Each rule has a target (which value to look at, here the refund's amount and reason), an operator and a value (the test to apply), and conditions (when the rule applies, here only for issue_refund). The two rules say: every refund must give a reason, and a refund above $500 is a serious violation. Because the agent is in block mode, a serious violation is blocked.

python/policies/refund-bot.yaml
name: refund-bot
version: "1.0.0"
description: >
  Rules for the Refund Bot. They check the proposed tool arguments at pre-check
  (execution.tools_called.0.arguments.*). Hard stops (an undeclared tool, an amount above the
  max_amount in the agent's manifest) come from the manifest, not from this pack.
environment: all
agent_id_patterns:
  - "refund-bot"

rules:

  - id: refund_reason_present
    description: "A refund must say why"
    severity: critical
    target: execution.tools_called.0.arguments.reason
    operator: not_empty
    conditions:
      - target: execution.tools_called.0.name
        operator: eq
        value: "issue_refund"

  - id: refund_over_500
    description: "A refund above $500 needs a person"
    severity: critical
    target: execution.tools_called.0.arguments.amount
    operator: lte
    value: 500
    conditions:
      - target: execution.tools_called.0.name
        operator: eq
        value: "issue_refund"

A model cannot read Python, so each tool needs a description for it: a name, what it does and what arguments it takes. tool_spec builds that automatically from the function's name, docstring and type hints. One detail: parameters that are keyword-only are skipped. We use that to give every tool two hidden extra values, user and input. The model never sees them and cannot fill them in, but the checkpoint reads them so AgentTrust knows who is asking and what the original request was.

python/app/llm/base.py
"""The model port. The agent loop talks to a ``Model`` and never imports a provider SDK."""from __future__ import annotations import inspectfrom dataclasses import dataclassfrom typing import Any, Callable, Protocol  @dataclassclass Message:    role: str                      # "user" | "assistant" | "tool"    content: Any    tool_call_id: str | None = None  @dataclassclass ToolSpec:    name: str    description: str    parameters: dict[str, Any]     # a JSON Schema object  @dataclassclass ToolCall:    id: str    name: str    args: dict[str, Any]  @dataclassclass FinalAnswer:    text: str  class Model(Protocol):    name: str     def next(self, messages: list[Message], tools: list[ToolSpec]) -> ToolCall | FinalAnswer: ...  _JSON_TYPES = {str: "string", float: "number", int: "integer", bool: "boolean"}  def tool_spec(fn: Callable[..., Any]) -> ToolSpec:    """Build a spec from a function's signature and docstring.     Keyword-only parameters are skipped: they carry hidden context (``user``, ``input``) that    the model must never see or fill in.    """    properties: dict[str, Any] = {}    required: list[str] = []    for name, param in inspect.signature(fn, eval_str=True).parameters.items():        if param.kind is inspect.Parameter.KEYWORD_ONLY:            continue        json_type = _JSON_TYPES.get(param.annotation)        if json_type is None:            raise TypeError(f"{fn.__name__}({name}): unsupported type hint {param.annotation!r}")        prop: dict[str, Any] = {"type": json_type}        if param.default is inspect.Parameter.empty:            required.append(name)        else:            prop["default"] = param.default        properties[name] = prop    doc = inspect.getdoc(fn) or ""    return ToolSpec(fn.__name__, doc.splitlines()[0] if doc else fn.__name__,                    {"type": "object", "properties": properties, "required": required})

Step 8 — The checkpoint itself (TODO 3)

This is the heart of the guide, so take your time. Open app/tools/governance.py. It only has a one-line description at the top. Everything below is yours to add. governed_harness takes one tool and returns a protected version of it. Inside, it uses the library's @harness, which does the asking. Our code around it adds four things the library does not do by default:

  • Stop on "needs review". If AgentTrust says a person should look first, treat that as a no. (The library lets it through by default.)
  • Stop on errors. If the check itself fails, do not run the tool. (The library runs the tool anyway by default.)
  • Turn refusals into results. Instead of crashing, a refusal returns BLOCKED and an unreachable gateway returns UNAVAILABLE. The bot reads these like any other result and reacts sensibly.
  • Say who is asking. @harness only learns the user from the call's keyword arguments, so we set it here. Without this line every record in the Console would show the user as unknown.

It also refuses to start if the gateway address or key is missing. Otherwise the library would quietly send its questions to localhost:8000, which is your own program, and run every tool unchecked.

python/app/tools/governance.py (green = lines you add)

Step 9 — Put the checkpoint around the tools (TODO 4)

Open app/tools/__init__.py. make_tools prepares every tool for the model: it fills in the context, adds the hidden values, and writes to the action log. It already accepts a governed option. Your job is the small green block that says "when governed is harness, use the checkpoint".

Pay attention to the order. The checkpoint goes on the outside, around the logging. So if AgentTrust says no, the code that writes the log line is never reached, and a blocked call leaves no trace in the action log. Step 10 — The agent loop (TODO 5)

The loop is short. It asks the model for the next step. If the model is finished it returns the answer, otherwise it runs the chosen tool, adds the result to the conversation, and repeats. A step limit stops a confused model from looping forever. That limit is a safety net for your program, not protection against misuse.

Look at how little changes: one green line passes the governed setting down to make_tools. The loop does not know what AgentTrust is. A BLOCKED result is, to the loop, just another result to hand back to the model.

7 · Safety and limits

What this setup protects, and where it stops:

  • Your key is limited by design. The agent key can only ask questions. It cannot change the manifest, the mode or the policies, so a leaked key cannot loosen the rules. Still, keep it in .env and rotate it in the Console if it leaks.
  • It refuses when it cannot ask. With AGENTRUST_FAILURE_MODE=closed, if the gateway cannot be reached, every tool is refused and the ticket stays open for a person. Setting it to open lets every tool run unchecked during an outage. Choose that only if a pause is worse than the risk.
  • It will not start half-configured. With no gateway address or key, the checkpoint raises an error instead of guessing.
  • Personal data stays out of the model. The customer lookup does not return the social security number or card number. Once a model has seen something, no later check can take it back, so the safest data is data it never receives.
  • It cannot wait for a human. When AgentTrust says a person should approve something, this method refuses the action. The reviewer's answer cannot be read back by an agent key, and the hosted gateway cannot reach a program running on your laptop to continue the work.
  • The check before does not read the customer's words. A hidden instruction is caught only by the check after, and only if the tool returns that text.
  • The check after cannot undo. It can hold a result back. It cannot reverse a tool that already ran.
  • Not measured here: how much time each guarded call adds, and the limits of your AgentTrust plan.

8 · If something goes wrong

The check says "rejected the key (HTTP 401)". The key in .env is not an agent key. Copy the at_live_… key again. A very long value starting with eyJ is a login token, not an agent key. (Also good to know: the gateway reads the key from a header called X-AgentTrust-Token. The library and our check send it for you, but if you test by hand with curl and only use Authorization: Bearer, you will get a 401.)
A $5,000 refund or "delete all orders" is approved. The agent has no tools listed in its manifest (Step 10), so AgentTrust skips the tool check. Open the agent, make sure the Tools line lists seven tools, and run the check again.
Every result says UNAVAILABLE. Your program cannot reach the gateway. Check the address in .env and your internet connection. Nothing ran and the ticket stays open, which is the safe outcome.
The program stops with GovernanceNotConfigured. The gateway address or the key is missing from .env. This is deliberate. Without them, the checks would go to your own program.
The Console shows the user as unknown. The line that sets the user in Step 8 is missing. @harness only reads the user from the call's keyword arguments.

When in doubt, run uv run refund-bot agenttrust check first. It finds most setup mistakes in a few seconds.
