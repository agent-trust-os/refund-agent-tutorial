Build a Governed Refund Bot

1 · What we are building

A support agent that works through a ticket the way a person on a help desk would: read the ticket, look up the order and the customer, decide, issue a refund, email the customer and close the ticket. It is a small FastAPI service plus a command line, with a database behind it.

An agent that can move money needs more than a good prompt. So this guide builds the bot in two parts that stay separate on purpose:

  • The agent — an API, an agent loop, a model and eight tools. It knows how to do the job.
  • The governance layer — a thin wrapper around every tool that asks AgentTrust "may this agent do this, with these arguments?" before the tool runs, and records the answer.

The model is a scripted, rule-based stand-in, so you need no model API key and every run is repeatable. Swapping in a real model later changes one file and nothing in the governance layer.

This guide builds the bot from scratch. If you would rather start from a working template and paste in seven numbered pieces, use the @harness setup reference. Both end in the same code.

2 · Why a governance layer

Without one, the model is the only thing between a customer's words and your payment system. We reproduced the failure on purpose: ticket T-1003 asks for $5,000 on a $120 order, and the ungoverned bot paid it.

  call      issue_refund {"order_id": "O-1003", "amount": 5000, "currency": "USD", "reason": "customer request"}
Answer: I refunded $5,000 for your order and emailed you a confirmation.
Ticket T-1006: open -> resolved
  4. issue_refund {"order_id": "O-1003", "amount": 5000, "currency": "USD", "reason": "customer request"}

Putting the check in the prompt does not help, because the prompt is the thing being attacked. A governance layer puts the check outside the model and in front of the tool:

  • Before the action. A refund above the agent's declared limit, or a tool the agent was never given, is refused before the tool body runs.
  • Rules in the Console. Limits, declared tools and policy rules change without a redeploy.
  • A record of every decision, with the reason and the arguments.
  • Designed in. Because the layer wraps tools generically, adding a ninth tool later gets the same protection for free.
2.1 · Pros and cons for this bot
ProsCons
Stops an action before it runs, whatever the model says.Two extra network calls per guarded tool call. Latency is not measured here.
Rules and limits change in the Console, no redeploy.One more service. When it is unreachable you choose refuse (fail closed) or run unchecked (fail open). The SDK default is fail open.
Every decision is recorded with its reason.Defaults fail open, and the default gateway URL is your own app. You can think you are protected when you are not.
Withholds a result that looks like a prompt injection.The pre-check does not read the customer's words, and a post-check cannot undo a tool that already ran.
About 60 lines; works under any agent loop.A call that needs a person is refused, not held and resumed.

3 · How it works

A request is a ticket. The agent loop asks the model what to do next, the model names a tool, and the loop runs it. The governance layer sits between "the loop runs a tool" and "the tool body executes".

3.1 · Components, and why
ComponentRole
API and CLI (FastAPI, argparse)A customer writes in; someone asks the agent to resolve the ticket.
Service (services/tickets.py)The workflow shared by the API and the CLI.
Agent loop (agents/support_agent.py)Asks the model, runs the tool it names, feeds back the result, repeats. It knows nothing about refunds.
Model (llm/)Decides the next tool call. Here a rule-based mock; a real LLM fits the same interface.
Tools (tools/)Eight plain functions over the database: read a ticket, look up an order, issue a refund, and so on.
Governance layer (tools/governance.py)Wraps each tool with @harness: asks AgentTrust before and after, turns refusals into plain results.
Action log (tools/action_log.py)One row per tool call that really ran. The proof of what happened.
AgentTrust gatewayAnswers approve or block, from the agent's manifest and policy pack.
3.2 · One tool call, end to end
  1. The model asks for issue_refund with an amount.
  2. The loop calls the tool the model was given, which is the guarded version.
  3. Pre-check: the tool name and arguments go to the gateway. It checks the tool is declared and within its limit, then scores the policy rules.
  4. On a block, BlockedError is raised, our wrapper returns {"status": "BLOCKED", …}, and the tool body never runs. The model sees a normal result and escalates the ticket.
  5. On an approve, the action is written to the action log and the tool runs.
  6. Post-check: the result goes to the gateway, which can withhold it, for example if it looks like an injection.
The package name. Install agentrust-py and import agentrust_sdk. The PyPI package called agentrust-sdk belongs to another company.

4 · Architecture

Four layers, one rule: each layer only talks to the one below it, and the governance layer is the only one that talks to AgentTrust.

Step 5 — Describe tools to the model

tool_spec builds what the model is shown (name, description, JSON schema) from a function's signature. Keyword-only parameters are skipped. That is how we hand each tool two hidden values, user and input, that the model can never see or fill in but that the governance layer reads.

python/app/llm/base.py
"""The model port. The agent loop talks to a ``Model`` and never imports a provider SDK."""from __future__ import annotations import inspectfrom dataclasses import dataclassfrom typing import Any, Callable, Protocol  @dataclassclass Message:    role: str                      # "user" | "assistant" | "tool"    content: Any    tool_call_id: str | None = None  @dataclassclass ToolSpec:    name: str    description: str    parameters: dict[str, Any]     # a JSON Schema object  @dataclassclass ToolCall:    id: str    name: str    args: dict[str, Any]  @dataclassclass FinalAnswer:    text: str  class Model(Protocol):    name: str     def next(self, messages: list[Message], tools: list[ToolSpec]) -> ToolCall | FinalAnswer: ...  _JSON_TYPES = {str: "string", float: "number", int: "integer", bool: "boolean"}  def tool_spec(fn: Callable[..., Any]) -> ToolSpec:    """Build a spec from a function's signature and docstring.     Keyword-only parameters are skipped: they carry hidden context (``user``, ``input``) that    the model must never see or fill in.    """    properties: dict[str, Any] = {}    required: list[str] = []    for name, param in inspect.signature(fn, eval_str=True).parameters.items():        if param.kind is inspect.Parameter.KEYWORD_ONLY:            continue        json_type = _JSON_TYPES.get(param.annotation)        if json_type is None:            raise TypeError(f"{fn.__name__}({name}): unsupported type hint {param.annotation!r}")        prop: dict[str, Any] = {"type": json_type}        if param.default is inspect.Parameter.empty:            required.append(name)        else:            prop["default"] = param.default        properties[name] = prop    doc = inspect.getdoc(fn) or ""    return ToolSpec(fn.__name__, doc.splitlines()[0] if doc else fn.__name__,                    {"type": "object", "properties": properties, "required": required})
Step 6 — Assemble the tools, and place the guard

make_tools turns the plain functions into what the model calls. It fills in the context, adds the hidden arguments, logs the action, and then (the governance part) wraps each tool with the guard. The guard is applied outside the logging wrapper, so a call that is blocked never reaches the action log. With no mode set the tools run as they are, so you can still reproduce the problem.

python/app/tools/__init__.py (green = added for governance)
"""The tools the agent can call. This is where AgentTrust guards each tool. With no mode set, tools run as they are.     It is applied outside the action log, so a blocked call never enters the log of what really ran. Step 7 — The governance layer

The heart of the guide. governed_harness wraps one tool with @harness and turns the SDK's exceptions into plain tool results, so the loop and the model see a normal answer. Three options exist because the SDK's defaults would let a risky call through: block_on_review, raise_on_error and the failure mode. It refuses to start with no gateway URL or key, rather than send checks to your own app on port 8000. And it sets user, because @harness reads it only from the call's keyword arguments.

python/app/tools/governance.py (green = added for governance)
"""AgentTrust governance for the tools: each tool is wrapped so AgentTrust is asked before it runs."""from __future__ import annotations import functoolsimport osfrom typing import Any, Callable from ..core.config import get_settings Tool = Callable[..., dict[str, Any]]  class GovernanceNotConfigured(RuntimeError):    """AgentTrust is asked for, but the gateway url or the key is missing."""  def governed_harness(tool: Tool) -> Tool:    """Guard a tool with ``@harness``: AgentTrust is asked before it runs, and again with what it returned.     A refused call comes back as a BLOCKED result and a gateway that cannot be reached as UNAVAILABLE, so    the agent loop and the model see a normal tool result instead of an exception.    """    settings = get_settings()    if not settings.agentrust_gateway_url or not settings.agentrust_key:        raise GovernanceNotConfigured("set AGENTRUST_GATEWAY_URL and AGENTRUST_KEY in .env (see .env-sample)")    os.environ.setdefault("AGENTRUST_FAILURE_MODE", settings.agentrust_failure_mode)    from agentrust_sdk import BlockedError, GatewayUnavailableError, harness     guarded = harness(        agent_id=settings.agentrust_agent_id,        action=tool.__name__,        base_url=settings.agentrust_gateway_url,        api_key=settings.agentrust_key,        block_on_block=True,        # a block stops the call        block_on_review=True,       # so does "a person must look first": the SDK default lets it through        raise_on_error=True,        # a failing check stops the call: the SDK default runs the tool anyway    )(tool)     @functools.wraps(tool)    def call(*args: Any, **kwargs: Any) -> dict[str, Any]:        kwargs.setdefault("user", "support-bot")        # @harness reads the user only from the keyword arguments        try:            return guarded(*args, **kwargs)        except BlockedError as exc:            return {"status": "BLOCKED", "tool": tool.__name__, "reason": exc.reason, "outcome": exc.outcome}        except GatewayUnavailableError as exc:            return {"status": "UNAVAILABLE", "tool": tool.__name__, "reason": str(exc)}        except Exception as exc:                        # the check itself failed: do not run the tool            return {"status": "UNAVAILABLE", "tool": tool.__name__, "reason": f"AgentTrust check failed: {exc}"}     return call
Step 8 — The agent loop

The loop asks the model, runs the tool it names, feeds the result back and repeats, with a step limit as a local safety net. It knows nothing about refunds and nothing about AgentTrust; the only governance-related line is passing governed to make_tools. A tool that raises becomes an ERROR result, and a BLOCKED or UNAVAILABLE result is just another result the model reacts to.

python/app/agents/support_agent.py (green = added for governance)
"""The agent loop: ask the model what to do, run the tool it names, give it the result, repeat. The loop knows nothing about refunds or tickets. It only moves messages between the model and the tools,so the model can be swapped (scripted, rule-based, later a real LLM) and the tools can be wrapped(by AgentTrust) without changing this file."""from __future__ import annotations import jsonimport loggingfrom typing import Any, Callable from sqlalchemy.orm import Session from ..llm.base import FinalAnswer, Message, Model, ToolCall, tool_specfrom ..repositories import records, ticketsfrom ..tools import make_toolsfrom .prompts import ticket_requestfrom .state import RunResult STEP_LIMIT_ANSWER = "Stopped: step limit reached" log = logging.getLogger("refund_bot.agent")  def call_tool(fn: Callable[..., dict[str, Any]], call: ToolCall, request: str) -> dict[str, Any]:    """Run one tool call. The request goes in as the hidden ``input`` argument. A tool that raises    becomes an ERROR result, so the model can recover instead of the loop crashing."""    try:        return fn(**call.args, input=request)    except Exception as exc:        return {"status": "ERROR", "tool": call.name, "reason": str(exc)}  def summary(result: dict[str, Any]) -> str:    """One short word for a tool result, for the log: ok, duplicate, an error, or BLOCKED and why."""    if result.get("status") in ("ERROR", "BLOCKED", "UNAVAILABLE"):        return f"{result['status']}: {result.get('reason', '')}"    if result.get("ok") is False:        return f"error: {result['error']}"    if result.get("status") == "duplicate":        return f"duplicate of {result['refund_id']}"    for key, label in (("refund", "refund_id"), ("ticket", "ticket_id")):        if key in result:            item = result[key]            return f"ok {item[label]}" + (f" ({item['status']})" if key == "ticket" else "")    return "ok"  def run(ticket_id: str, model: Model, db: Session, max_steps: int = 10, governed: str | None = None) -> RunResult:    """Work on one ticket until the model gives its final answer.     ``max_steps`` is a local safety net so a looping model cannot run forever. It is not a governance control.    ``governed`` says how AgentTrust guards the tools: None (not at all), "harness" or "client".    """    tools = make_tools(db, ticket_id, governed)    specs = [tool_spec(fn) for fn in tools.values()]    before = {t["ticket_id"] for t in tickets.list_tickets(db)}    request = ticket_request(ticket_id)    messages = [Message("user", request)]    answer = STEP_LIMIT_ANSWER    log.info("%s | start | model=%s", ticket_id, getattr(model, "name", type(model).__name__))     for _ in range(max_steps):        step = model.next(messages, specs)        if isinstance(step, FinalAnswer):            answer = step.text            messages.append(Message("assistant", answer))            break        messages.append(Message("assistant", {"tool": step.name, "args": step.args}, tool_call_id=step.id))        fn = tools.get(step.name)        if fn is None:            result = {"status": "ERROR", "tool": step.name, "reason": f"unknown tool {step.name!r}"}        else:            result = call_tool(fn, step, request)        log.info("%s | call  | %s %s -> %s", ticket_id, step.name, json.dumps(step.args), summary(result))        log.debug("%s | result | %s", ticket_id, json.dumps(result))        messages.append(Message("tool", result, tool_call_id=step.id))     ticket = tickets.get_ticket(db, ticket_id)    log.info("%s | done  | ticket %s | answer: %s", ticket_id, ticket["status"] if ticket else "missing", answer)    return RunResult(        ticket_id=ticket_id,        transcript=messages,        answer=answer,        ticket=ticket,        actions=records.list_actions(db, ticket_id=ticket_id),        created_tickets=[t for t in tickets.list_tickets(db) if t["ticket_id"] not in before],    )

Step 10 — Create the agent in the Console

The agent is what the gateway knows your bot by. Its key is what the app uses to ask questions, and it can reach only the runtime checks, never the Console settings.

  1. Sign in to the Console and open Agents. Create an agent named refund-bot with mode block.
  2. Copy the API key when it is shown. It starts with at_live_ and appears only once. Never paste it into a chat, a ticket or a commit.

Step 11 — Add the policy pack

The manifest cap is a hard stop. The policy pack adds score-based rules on the arguments. In Policies create a private pack, paste the YAML below and activate it. A refund needs a reason, and a refund above $500 is a critical violation; in block mode a violation is blocked.

python/policies/refund-bot.yaml
name: refund-bot
version: "1.0.0"
description: >
  Rules for the Refund Bot. They check the proposed tool arguments at pre-check
  (execution.tools_called.0.arguments.*). Hard stops (an undeclared tool, an amount above the
  max_amount in the agent's manifest) come from the manifest, not from this pack.
environment: all
agent_id_patterns:
  - "refund-bot"

rules:

  - id: refund_reason_present
    description: "A refund must say why"
    severity: critical
    target: execution.tools_called.0.arguments.reason
    operator: not_empty
    conditions:
      - target: execution.tools_called.0.name
        operator: eq
        value: "issue_refund"

  - id: refund_over_500
    description: "A refund above $500 needs a person"
    severity: critical
    target: execution.tools_called.0.arguments.amount
    operator: lte
    value: 500
    conditions:
      - target: execution.tools_called.0.name
        operator: eq
        value: "issue_refund"

7 · Security & limits

  • The agent key reaches only the runtime checks. It cannot change the manifest, the mode or the policies.
  • The key lives in .env, which git ignores. Rotate it in the Console if it leaks.
  • AGENTRUST_FAILURE_MODE=closed refuses every tool when the gateway is unreachable, and the ticket stays open for a person. open lets every tool run unchecked.
  • The guard refuses to start with no gateway URL or key.
  • The customer lookup does not return the SSN or card number: once a model has seen personal data, no check can take it back.
  • It cannot hold a call for a person and resume it. A call that needs review is refused; the hosted gateway cannot call back to an app on your laptop.
  • The pre-check does not read the customer's words. Injection is caught only by the post-check on a tool that returns the text.
  • A post-check cannot undo. It withholds a result; it does not reverse a tool that already ran.
  • Not measured here: latency per guarded call and your plan's limits.

8 · Troubleshooting

The check says "rejected the key (HTTP 401)" — the key in .env is wrong. Copy the at_live_… key again; a long token starting eyJ is a login token, not an agent key. The gateway reads the key from an X-AgentTrust-Token header, which the SDK and the check send for you; a hand-written curl with only Authorization: Bearer gets a 401.
A $5,000 refund or purge_orders is approved — the manifest has no declared tools (Step 10), so the gateway skips the tool check. Confirm the Tools line lists seven tools and run the check again.
Every result is UNAVAILABLE — the gateway cannot be reached and the failure mode is closed. Check AGENTRUST_GATEWAY_URL and your network. Nothing ran and the ticket stays open: this is the safe failure.
GovernanceNotConfigured on start — AGENTRUST_GATEWAY_URL or AGENTRUST_KEY is missing from .env. That is intended: it would otherwise send checks to your own app.
The Console shows the user unknown — the setdefault("user", …) line in the guard is missing; @harness reads the user only from keyword arguments.

If something isn't working, run uv run refund-bot agenttrust check first; it catches most setup issues.
