1 · What is @harness?

AgentTrust is a governance service for AI agents. Your agent calls tools (issue a refund, delete orders, send an email); AgentTrust sits beside it and answers one question for each call: may this agent do this, with these arguments, right now? The answer is recorded, and a "no" stops the action.

@harness is the connection mode that puts that question in front of each tool. It is a Python decorator from the AgentTrust SDK. Wrapped around a tool function, it asks the gateway before the function runs, runs it only if the answer is yes, then sends the result back for a second check.

The Refund Bot is a support agent: it reads a ticket, looks up the order and customer, issues a refund, emails the customer and closes the ticket. A scripted, rule-based model drives it, so you need no model API key and every run is the same. That makes it a safe place to see what goes wrong without it:

2 · Why we use it

A refund tool moves real money and cannot be undone, so it is exactly the kind of tool you want checked by something other than the model that asked for it:

  • The check happens before the action. A refund above the agent's declared limit, or a tool the agent was never given, is refused before the tool body runs.
  • Rules live in the Console, not in code. Limits, declared tools and policy rules change without a redeploy.
  • Every decision is recorded. Each check shows up in the Console with its decision, reason and arguments.
  • It is small. About 60 lines of Python, and it works under any agent loop.

3 · How it works

For each tool call, @harness makes two requests to the gateway's runtime API (/v1/runtime/pre-check and /v1/runtime/post-check), authenticated with the agent's own key. There is no model call inside AgentTrust: the checks are deterministic rules.

3.1 · Components, and why

The package name. Install agentrust-py. You import it as agentrust_sdk. The PyPI package called agentrust-sdk belongs to another company.
3.2 · What happens on one tool call

Nothing secret leaves your app except the tool name, its arguments and its result:

  1. Pre-check — the tool name and arguments go to the gateway. It checks the tool is declared in the manifest and within its limit (a hard stop), then scores the policy rules.
  2. Decision — approve, or block. A block raises BlockedError and the tool body never runs.
  3. The tool runs — only after an approve.
  4. Post-check — the result goes to the gateway, which can withhold it, for example if it looks like a prompt injection. This cannot undo what the tool already did.

Three SDK defaults would let a risky call through: block_on_review=False, raise_on_error=False and a failure mode of open. Our wrapper sets all three the safe way.

4 · Architecture

The setup is deliberately small: one wrapper around each tool, one agent in the Console, nothing else in the request path.

6 · Setup steps

This is what actually has to happen, in order, to get the Refund Bot from "any tool call runs" to "the gateway is asked first". You need Python 3.12, uv and an account at https://console.agent-trust.tech.

From Step 7 on you edit the code. Each step names a file and shows a block of code: replace the TODO comment line with it. Every edit only adds code, so nothing else has to be removed or rewritten. Removing the comment is also what makes ./scripts/todos.sh count the step as done.

Step 1 — Download the template

The tests run with no keys and no network, so you can confirm the starting point works before changing anything.

Step 2 — Create the agent and its key in the Console

The agent is what the gateway knows your bot by. Its key is what your app uses to ask questions, and it can only reach the runtime checks, never the Console settings.

  1. Sign in to the Console and open Agents.
  2. Create an agent named refund-bot with mode block.
  3. Copy the API key when it is shown. It starts with at_live_ and appears only once. Never paste it into a chat, a ticket or a commit.

Step 3 — Declare the manifest

The manifest tells the gateway which tools this agent may use and the largest refund it may make. Open the agent, find Manifest & fingerprint, then under CERTIFY.YAML click Paste… and paste python/policies/refund-bot.certify.yaml. It declares seven tools, leaves out purge_orders and sets max_amount: 1000 on issue_refund. The Tools line in the manifest section should then list seven tools.

Do not skip this. With no declared tools the gateway skips the tool check and approves anything, including a tool that does not exist. We saw exactly that: before the manifest was saved, purge_orders was approved.
Step 4 — Add the policy pack

The manifest cap is a hard stop; the policy pack adds score-based rules on the arguments. In Policies create a private pack, paste the YAML below (it is the file python/policies/refund-bot.yaml) and activate it. It has two rules: a refund needs a reason, and a refund above $500 is a critical violation. In block mode a violation is blocked.

{{file:python/policies/refund-bot.yaml}}

Read it from the top. agent_id_patterns ties the pack to your refund-bot agent. Each rule has a target, the path of the value to check inside the proposed call (execution.tools_called.0.arguments.amount is the refund amount), an operator and a value. The conditions block limits a rule to calls of issue_refund, so lookups are never affected. A critical rule that fails drops the policy score to 0, and the gateway then blocks.

7 · Security & limits

  • The agent key reaches only the runtime checks. It cannot change the manifest, the mode or the policies.
  • The key lives in .env, which git ignores. Rotate it in the Console if it leaks.
  • AGENTRUST_FAILURE_MODE=closed refuses every tool when the gateway is unreachable, and the ticket stays open for a person. open lets every tool run unchecked.
  • Governed mode refuses to start with no gateway URL or key.
  • No SSN or card number is returned to the model.
  • It cannot hold a call for a person and resume it. A call that needs review is refused. The hosted gateway cannot call back to an app on your laptop, and an agent key cannot read the reviewer's answer.
  • The pre-check does not read the customer's words. Injection is caught only by the post-check on a tool that returns the text.
  • A post-check cannot undo. It withholds a result; it does not reverse a tool that already ran.
  • It returns no event id for an allowed call, so you cannot link a run to its Console event from the app. The direct API guide shows how.
  • Not measured here: latency per guarded call and your plan's limits.

8 · Troubleshooting

The check says "rejected the key (HTTP 401)" — the key in .env is wrong. Copy the at_live_… key again; a long token starting eyJ is a login token, not an agent key. The gateway reads the key from an X-AgentTrust-Token header; the SDK and the check send it for you, but a hand-written curl with only Authorization: Bearer gets a 401.
A $5,000 refund or purge_orders is approved — the manifest has no declared tools (Step 3), so the gateway skips the tool check. Open the agent, confirm the Tools line lists seven tools, and run the check again.
Every result is UNAVAILABLE — the gateway cannot be reached and the failure mode is closed. Check AGENTRUST_GATEWAY_URL and your network. Nothing ran, and the ticket stays open. This is the safe failure.
The Console shows the user unknown — the kwargs.setdefault("user", …) line from TODO 3 is missing. @harness reads the user only from keyword arguments.
The checks look fine but nothing is recorded in Events — AGENTRUST_GATEWAY_URL may be missing, so checks went to your own app on port 8000. Governed mode refuses to start in that case; if you changed the code, put the check back.

If something isn't working, run uv run refund-bot agenttrust check and ./scripts/todos.sh. Those two catch most setup issues.
